= Image Metadata processing using Java

image:https://github.com/ghillert/image-metadata/workflows/Java%20CI%20with%20Maven/badge.svg[CI Image Metadata,link=https://github.com/ghillert/image-metadata/actions]

This repository contains examples for processing image metadata using Java. Currently, the following module
is available:

- *image-metadata-commons-imaging*

This https://spring.io/projects/spring-boot[Spring Boot] 3 application will allow you to upload images (JPG, PNG, GIF)
and the application will extract the metadata from those files using
https://commons.apache.org/proper/commons-imaging/[Apache Commons Imaging]. This includes:

- *EXIF* (Exchangeable image file format)
- *IPTC* (International Press Telecommunications Council)
- *XMP* (eXtensible Metadata Platform)
- Generic *file* metadata

To learn more about the alphabet soup, see my blog post:
https://medium.com/@hillert/read-write-image-metadata-with-java-part-1-d5e2057c80d9[Read & Write Image Metadata with Java — Part 1]
This demo application also provides the following additional features:

- Remove all image metadata
- Populate image metadata such as image title and reference id
- Ability to resize images
- Slightly sharpen resized images using a Gaussian Unsharp Mask
- Add a font label to resized images
- Ability to load images using ImageIO or AWT Toolkit (To study performance differences)
- Ability to download the stored image

NOTE: Image metadata is manipulated during file upload. Any other manipulation such as resizing is done during image
retrieval. This is purely a demo app and not meant to be production ready.

== UI Options

=== File upload

The main input field (and only mandatory input field) is the file upload option. You can select
any image of the following type to extract metadata from:

- JPG
- PNG
- GIF

=== Title

The title input field, will populate

- the XMP `Title` tag of the Dublin Core namespace.
- the IPTC `Object Name` field
- the EXIF `Image Description` Field

In case you also selected the `Remove Metadata` checkbox, we will also populate the `XPTitle` EXIF tag.

- https://exiftool.org/TagNames/XMP.html#dc[XMP Dublin Core (dc) namespace tags]
- https://exiftool.org/TagNames/EXIF.html
- https://exiftool.org/TagNames/IPTC.html#ApplicationRecord

=== Reference ID

Populates the IPTC field `OriginalTransmissionReference` as well as the XMP tag `TransmissionReference`. These two fields
are commonly used as a job identifier. So if you need to tie your images to e.g. a database record, this might be a useful
field to know about. For more information, please also see the following links for more information:

- https://exiftool.org/TagNames/XMP.html#photoshop[XMP photoshop Tags]
- https://exiftool.org/TagNames/IPTC.html#ApplicationRecord[IPTC ApplicationRecord Tags]

=== Remove Metadata

Removes all _IPTC_, _EXIF_ and _XMP_ metadata.

=== Populate Windows Tags

The following tags are the Windows-specific exif tags:

- XPTitle (Populated by EXIF tag ImageDescription)
- XPComment
- XPAuthor (Populated by EXIF tag Artist)
- XPKeywords
- XPSubject
- Rating
- RatingPercent

If the checkbox is selected AND the Caption/Title input field is populated, we will populate the `xptitle` tag.
Please also see the EXIF tag documentation at https://exiftool.org/TagNames/EXIF.html.

== Going Native

Native compilation has been a bit of a moving target when using AWT classes. Luckily, the situation is
continuously improving. For instance, until recently the story on Windows was a bit more involved, requiring
to compile the project using the *x64 Native Tools Command Prompt for VS 2022* (See the following
https://medium.com/graalvm/using-graalvm-and-native-image-on-windows-10-9954dc071311[blog post]
for more information.)

Luckily as of GraalVM for JDK 17.0.8 the situation on Windows is much improved -
See the following https://medium.com/graalvm/a-new-graalvm-release-and-new-free-license-4aab483692f5[blog post]
for details.

*IMPORTANT*

AWT and ImageIO native-image metadata can depend on the JDK version and platform.
For reference, `image-metadata-commons-imaging/src/main/resources/META-INF` contains the following platform snapshots:

- native-image-linux
- native-image-mac
- native-image-windows

These platform folders are historical snapshots. The active `native-image` folder includes JDK 25 font JNI updates;
do not replace it with an older snapshot without collecting and validating fresh metadata.
You can run the *native-image-agent* as described under *Development* below.

=== Creating a Local Native Image

Creating a local image should be as easy as:

[source,bash,indent=0,subs=attributes]
----
./mvnw clean package -DnativeCompile
----

This shorthand system property will activate the Maven profiles:

- native
- nativeCompile

So you can also use:

[source,bash,indent=0,subs=attributes]
----
./mvnw clean package -Pnative,nativeCompile
----

The native profile uses the libraries' default class-initialization settings. Forcing SLF4J, Logback, or JavaBeans
classes to initialize at build time fails GraalVM 25's strict image-heap checks (for example,
`SubstituteServiceProvider` or `ClassInfo$1` in the image heap).
JTE's `generate` goal runs `NativeResourcesExtension` to register the compiled templates for reflection.
The Java compiler then compiles those generated sources along with the application.

The result (if successful) will be an executable binary at: `image-metadata-commons-imaging/target/image-metadata-commons-imaging`

TIP: You can use https://upx.github.io/[Ultimate Packer for eXecutables] (UPX) to further compress the binary. E.g.
`upx -9 image-metadata-commons-imaging/target/image-metadata-commons-imaging`

NOTE: UPX is currently broken on MacOS 13. See the relevant https://github.com/upx/upx/issues/612[GitHub issue ticket]
for details.

==== macOS

Liberica NIK `25.0.5.0+3.1-nik` supports both resizing and the Swing filename labels in this application.
Use NIK as `JAVA_HOME` when invoking Maven (for example, `sdk use java 25.0.5.0+3.1-nik`), then run:

[source,bash]
----
./mvnw clean package -DnativeCompile
python3 scripts/check-native-images.py image-metadata-commons-imaging/target/image-metadata-commons-imaging
----

The smoke check starts the executable on a temporary loopback port with isolated upload storage and AI disabled.
It uploads a JPEG, checks 200- and 800-pixel output dimensions, and checks that filename labels change the images.
Serving the original file as a fallback fails this check. No external service or Python package is required.

NIK 25 has a macOS AWT loading regression: it links `awt_lwawt` statically, but `JVM_IsStaticallyLinked()`
returns false. The https://github.com/openjdk/jdk25u/blob/master/src/java.desktop/unix/native/libawt/awt/awt_LoadLibrary.c[AWT loader]
then tries to open a nonexistent `libawt_lwawt.dylib` beside the executable.
The matching loading failure is reported in https://github.com/bell-sw/LibericaNIK/issues/38[LibericaNIK issue #38].
`LibericaMacAwtLibraries` routes that specific request through Native Image's built-in library loader.
The automatically activated `liberica-nik-25-macos-awt` Maven profile retains and exports
`JNI_OnLoad_awt_lwawt`, which NIK otherwise omits from its built-in initializer map.
The substitution is restricted to NIK 25 on macOS; the linker profile requires macOS, BellSoft, and JDK 25.
This does not modify the installed JDK or require copying its shared libraries beside the executable.
Recheck whether this compatibility workaround is needed when upgrading NIK.

Resizing and labels are enabled by default (`metadata.do-not-resize=false`). Setting it to `true` serves stored
images directly. If a native library or image-processing class cannot load, the endpoint logs a warning and serves
stored images for the rest of that process; this fallback preserves availability but does not resize or label images.

Oracle GraalVM `25.4.4.1+1-graal` builds the application on macOS Apple Silicon and copies the required `.dylib`
files into `target` beside the executable. Keep these libraries alongside the executable when moving it.
Native smoke checks pass for startup, JTE pages, static assets, upload, metadata details, and image resizing with
`addLabel=false`. This does not establish full AWT/Swing compatibility on macOS.

JDK 25 font rendering needs JNI registrations for `Font2D.charToGlyphRaw`, `Font2D.charToVariationGlyphRaw`, and
`FontUtilities.debugFonts`. These are included in the active `META-INF/native-image/jni-config.json`.
Without them, adding a filename label to an image can fail with `NoSuchMethodError` even though compilation succeeds.

[WARNING]
====
Labeled image rendering remains limited on macOS with this Oracle GraalVM version. Without `java.home`, font initialization
fails with `java.home property not set`. Supplying the GraalVM JDK as `java.home` gets past font initialization,
but the current Swing `JLabel` renderer then blocks in `LWCToolkit_getMultiClickTime`, waiting on the macOS main thread.
This was reproduced with a native request and confirmed with a process stack sample. Use the JVM application for
labeled images or use the verified Liberica NIK build. Oracle native resizing works with `addLabel=false`;
labeling still has the limitation above.
====

./image-metadata-commons-imaging/target/image-metadata-commons-imaging

==== Linux

Once compiled you need to provide the `java.home` to the executable. This is needed to load the font sub-system. However,
the contents of `java.home` just needs one file `fontconfig.properties` with the contents:

[source,properties]
----
version=1
sequence.allfonts=default
----

[NOTE]
====
This was previously for the Windows executable as well but seems to work now without. So maybe this may not be needed
eventually. For more information see:

- https://github.com/adoptium/temurin-build/issues/693
- https://www.jianshu.com/p/a53ae350f845?v=1669292961020
====

For simplicity, the project provides a `fontconfig.properties` file. Therefore, once the binary is created, launch the
application using:

[source,bash]
----
./image-metadata-commons-imaging/target/image-metadata-commons-imaging \
-Djava.home=iage-metadata-commons-imaging/src/lib/
----

[NOTE]
====
You may also need to install `libfreetype6-dev`:

[source,bash]
----
apt install gcc zlib1g-dev build-essential libfreetype6-dev
----

See also: https://github.com/graalvm/mandrel/issues/189
====

== UI development

The UI uses Tabler components and typed JTE templates. Like Pembana, frontend assets are
bundled with npm and Webpack; like Pembana Rain Gauge, shared JTE layouts are precompiled
into the application. CSS and JavaScript are served locally, with no runtime CDN dependency.
The GPS map uses OpenStreetMap tiles and requires an internet connection.

`./mvnw clean verify` installs a pinned, project-local Node runtime, runs `npm ci`, builds
assets into `target/frontend`, and generates and compiles JTE templates with their native-image metadata. No global Node installation
is required. The frontend package and lockfile live in `image-metadata-commons-imaging`.
All Maven dependency and plugin versions remain properties in the parent POM.

For frontend-only iteration, run `npm ci` and `npm run watch` from that module using Node 24.
After rebuilding, run `./mvnw process-resources` from the module to copy the assets into
the application classpath. Templates are in `src/main/jte`; frontend sources are in
`src/main/frontend`. Generated assets and node_modules are excluded from Git.

To run the app, first package it, then use:

[source,bash]
----
java -jar image-metadata-commons-imaging/target/image-metadata-commons-imaging-1.0.0-SNAPSHOT.jar
----

JTE uses precompiled templates by default, including tests and packaged runs. Template
changes require rebuilding. Existing image processing and AI configuration still apply.

== Optional AI image descriptions

The application starts without an OpenAI API key. Missing or blank keys disable AI image descriptions;
upload, previews, metadata inspection, and editing remain available. The details page displays
"Image descriptions are disabled." No OpenAI clients or Spring AI auto-configurations are started in this mode.

To enable descriptions, set `OPENAI_API_KEY` (or `spring.ai.openai.api-key`) and leave
`metadata.ai.create-image-description=true`. Set that flag to `false` to disable AI even when a key is present.
The application creates only the chat client it needs; it does not auto-configure embedding, audio, or image-generation models.
Configuration is evaluated at application startup, including native execution, so a key is not required when building.

Use `spring.ai.openai.chat.model` to choose the chat model. The older `spring.ai.openai.chat.options.model`
setting remains supported. Chat-specific `api-key` and `base-url` settings override their common OpenAI equivalents.
If an enabled AI service fails during a request, the details page retains the metadata and shows the existing
description-unavailable message.
